## 功能修复清单

P1 表示建议优先修复的隔离、数据丢失或主要功能错误；P2 表示下一批修复。这里是工程优先级，不是漏洞严重性评级。每项按所列验收条件完成即可，不需要扩大为通用框架。

### R01 · P1 · 给子代理 session 增加调用者隔离

- [x] 将会话键至少改为 `(caller, session_id)`；status、续写、steer、stop、cancel、后台任务控制和目录查询使用同一归属规则。

**证据：** [subagent/session.rs:843](https://github.com/ldclabs/anda/blob/5fb492554d943fae8a9d6d364ef2a4f90adb2e5b/anda_engine/src/subagent/session.rs#L843) 的全局表只按 `String` 索引；[subagent/agent.rs:234](https://github.com/ldclabs/anda/blob/5fb492554d943fae8a9d6d364ef2a4f90adb2e5b/anda_engine/src/subagent/agent.rs#L234) 和 313 行查找时没有 caller。`SubAgent` 的克隆共享 `Arc<SubSessions>`。诊断中 A 启动 `shared` 会话，B 查询同名 session，读到了 A 的 `last_progress`。

**影响：** 共用一个引擎的普通多用户请求会串会话，B 的后续输入也会进入 A 的运行上下文。单用户部署不受跨用户影响。

**最小改法：** 内部增加结构化归属键；不要仅靠调用方给 session 字符串加前缀。manager 的 session 列表按 caller 过滤。

**验收：** 两个不同 principal 使用相同 session ID，进度、消息、停止操作完全独立；同一 caller 的复用行为保持。

### R02 · P1 · 修复 store_list(None) 越过 namespace

- [x] 未提供 prefix 时仍向底层 ObjectStore 传入 namespace 前缀。

**证据：** [store.rs:184](https://github.com/ldclabs/anda/blob/5fb492554d943fae8a9d6d364ef2a4f90adb2e5b/anda_engine/src/store.rs#L184) 将 `None` 原样保留；只把 offset 拼上 namespace。诊断写入 `a/file` 与 `z/file` 后，`store_list(a, None, root)` 返回了两者。

**影响：** 列出其他组件的对象路径及元数据，破坏文档中的存储隔离；这不等于能够直接读取其他 namespace 的内容。

**最小改法：** 显式前缀为 `namespace + relative_prefix`，无前缀则使用 namespace；保留 root namespace 的合法全局行为。

**验收：** 覆盖无前缀、空前缀、子前缀、分页 offset；非 root namespace 的每个结果均属于自身前缀。

### R03 · P1 · 修复发现 schema 的缓存与压缩一致性

- [x] 目录摘要不作为完整 schema 缓存；后续完整定义能升级旧摘要；只有确实合入本轮 request 的 schema 才能从工具输出移除。

**证据：** [context/tool.rs:244](https://github.com/ldclabs/anda/blob/5fb492554d943fae8a9d6d364ef2a4f90adb2e5b/anda_engine/src/context/tool.rs#L244) 的 `tools_search("*")` 返回 `parameters: {}`；[context/tool.rs:144](https://github.com/ldclabs/anda/blob/5fb492554d943fae8a9d6d364ef2a4f90adb2e5b/anda_engine/src/context/tool.rs#L144) 用 `or_insert`，后续 `tools_select` 返回的完整 schema 无法覆盖。另一个诊断一次选择 17 个工具：144–147 行只缓存前 16 个，[context/tool.rs:190](https://github.com/ldclabs/anda/blob/5fb492554d943fae8a9d6d364ef2a4f90adb2e5b/anda_engine/src/context/tool.rs#L190) 却压缩了全部 17 个，导致最后一个的 schema 两边都没有；受限 runner 还会拒绝它。

**最小改法：** 让“发现/目录条目”和“已载入完整 schema”在现有 `DiscoveredTools` 内有明确区别；用本轮实际合并的名称集合决定压缩。无需另建发现服务。

**验收：** `* → select` 能获得完整参数；选择/扩展 17+ 成员的组时，所有返回工具的 schema 至少保留在 request 或工具输出的一处；未载入项不会被误报已载入。

### R04 · P1 · Anthropic 服务端工具不能进入本地调用队列

- [x] 将 `ServerToolUse` 留作 provider 历史/中立历史中的非执行内容；只有客户端 `ToolUse` 产生待执行 `ToolCall`。

**证据：** [model/anthropic/types.rs:1256](https://github.com/ldclabs/anda/blob/5fb492554d943fae8a9d6d364ef2a4f90adb2e5b/anda_engine/src/model/anthropic/types.rs#L1256) 合并了 `ServerToolUse` 与 `ToolUse`；1450 行统一提取 `msg.tool_calls()`。诊断给出完整 `server_tool_use + web_search_tool_result + text`，仍产生一个待执行 `web_search`。

**影响：** 服务端已处理的搜索又被 runner 当成本地工具执行，产生重复副作用、找不到工具的错误或多余模型轮次。

**协议核对：** 服务端工具由 Anthropic 执行；即便与客户端工具混合返回，也只需回送客户端工具结果。[官方说明](https://platform.claude.com/docs/en/agents-and-tools/tool-use/server-tools)。

**验收：** 服务端工具单独返回、与客户端工具混合返回两种 fixture；仅客户端工具被分派。保存/恢复历史仍保留服务端信息，raw history 的签名处理不变。

### R05 · P1 · OpenAI Responses 流错误不能被当作成功

- [x] 识别 SSE `error` 事件；流结束时检查是否获得终态响应，不能把 `created/in_progress` 当完成。

**证据：** [model/openai/types.rs:424](https://github.com/ldclabs/anda/blob/5fb492554d943fae8a9d6d364ef2a4f90adb2e5b/anda_engine/src/model/openai/types.rs#L424) 没有 error 分支；[model/openai.rs:1218](https://github.com/ldclabs/anda/blob/5fb492554d943fae8a9d6d364ef2a4f90adb2e5b/anda_engine/src/model/openai.rs#L1218) 忽略其他事件，保留最后一份 response；[model/openai/types.rs:2618](https://github.com/ldclabs/anda/blob/5fb492554d943fae8a9d6d364ef2a4f90adb2e5b/anda_engine/src/model/openai/types.rs#L2618) 不把 InProgress 视为失败。诊断服务器先返回 `response.created`，再返回 `error: server_error` 并结束；适配器返回空内容且 `failed_reason=None`。

**最小改法：** 在 Responses 自己的聚合器里处理错误和 terminal 状态；按现有 `ModelError` 规则标记可重试错误。

**验收：** created→error、created→正常结束、created→非终态 EOF、completed→EOF 四条路径，错误不能成为成功空回答。

### R06 · P1 · Gemini 使用正确的 JSON Schema 字段

- [x] 通用 JSON Schema 使用 `parametersJsonSchema` / `responseJsonSchema`，或明确转换成 Gemini OpenAPI Schema；二者不要混用。

**证据：** [model/gemini/types.rs:610](https://github.com/ldclabs/anda/blob/5fb492554d943fae8a9d6d364ef2a4f90adb2e5b/anda_engine/src/model/gemini/types.rs#L610) 将通用定义直接装入 `parameters`；[model/gemini.rs:313](https://github.com/ldclabs/anda/blob/5fb492554d943fae8a9d6d364ef2a4f90adb2e5b/anda_engine/src/model/gemini.rs#L313) 将 `output_schema` 装入 `responseSchema`。诊断使用内置 todo 工具，生成了 `parameters.properties.op.type=["string","null"]`。

**契约不匹配：** 官方 `Schema.type` 是单个枚举，nullable 是独立布尔字段；`parametersJsonSchema` 才接收 JSON Schema。[Gemini API](https://ai.google.dev/api/generate-content#FunctionDeclaration)、[Schema](https://ai.google.dev/api/generate-content#Schema)。当前普通含 `Option` 的工具就会触及此问题；不需要复杂 schema 才出现。

**验收：** todo/note 的 nullable 字段、嵌套对象、required、结构化输出做出站 wire 测试；使用官方兼容校验/集成环境验证。此次未声称实测了真实 API 的错误码。

### R10 · P1 · Stream 等待期间追加的消息不能丢失

- [x] 将 stream 的输入队列在正常终态提交之前交给真实 runner。

**证据：** [context/runner.rs:1252](https://github.com/ldclabs/anda/blob/5fb492554d943fae8a9d6d364ef2a4f90adb2e5b/anda_engine/src/context/runner.rs#L1252) 在 `runner.next()` 完成后才恢复和交付缓冲输入；若本轮正常结束已设置 `done=true`，[context/runner.rs:325](https://github.com/ldclabs/anda/blob/5fb492554d943fae8a9d6d364ef2a4f90adb2e5b/anda_engine/src/context/runner.rs#L325) 会忽略 follow_up。诊断在 Pending 时追加第二条消息，首条回复完成后 stream 直接 None，第二条消息消失。steer 存在同一路径。

### R11 · P2 · handoff 失败不能耗尽原 runner

- [x] 摘要生成与原 runner 的终态提交分离，摘要成功后才替换会话状态。

**证据：** [context/runner.rs:732](https://github.com/ldclabs/anda/blob/5fb492554d943fae8a9d6d364ef2a4f90adb2e5b/anda_engine/src/context/runner.rs#L732) 调用 `finalize`；输出失败或空摘要时进入恢复分支，但 [context/runner.rs:749](https://github.com/ldclabs/anda/blob/5fb492554d943fae8a9d6d364ef2a4f90adb2e5b/anda_engine/src/context/runner.rs#L749) 没恢复 `done`、被 final_output 取走的历史和累计数据。诊断 `failed_reason=max_tokens` 后 `handoff` 返回 Err，原 runner 却已 done，无法追加重试。

**最小改法：** 使用独立摘要请求/临时 runner；只在成功时提交新状态。已经执行过的 pending tools 不可因重试再执行。

**验收：** 网络 Err、failed_reason、空摘要三类失败都能继续原任务；历史和 usage 不丢失；成功路径仍清掉 provider raw state。

### R13 · P2 · 让前台 shell 与会话控制真正响应取消

**验收：** 前台等待、后台运行、runner future 被丢弃、子代理模型等待中取消；进程树不继续工作，输出 reader 被回收。Unix/Windows 分别按可用机制验证，不顺带实现新的 shell sandbox。
